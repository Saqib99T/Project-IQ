Overview

Four capabilities were added on top of the existing ticketing core, each building on the last: ticket‑level SLA/OLA/UC tracking replaced the old flat SLA‑policy field with agreements, versioned targets, and breach attribution; on‑call & incident response added PagerDuty‑style paging, escalation, and an incident command workflow; SLI/SLO reliability layered telemetry‑fed error budgets on top of the on‑call services graph; and support recording + RCA governance — the newest piece — lets agents attach Teams/SharePoint recordings as evidence and enforces that serious incidents get a reviewed, approved root‑cause report with tracked corrective actions.

01

SLA / OLA / UC Management

built

Shipped 2026‑07‑01. Replaces the old single SLAPolicy (flat response/resolution + a business‑hours flag) with a full JSM/Zoho‑grade ticket‑SLA engine: versioned agreements, per‑metric targets, vendor/team underpinning chains, priority‑ordered matching, and coverage‑window‑aware clocks.

What it does

  • Agreements with a kind — sla, ola, or uc — each independently versioned, so editing an agreement never retroactively changes a ticket's already‑running clock.
  • Per‑metric targets (first response, periodic update, resolution, …) scoped by priority, ticket type, or category, each with its own coverage window and 50/75/90% warning thresholds.
  • OLA/UC underpinning chains — an SLA can be backed by an internal team OLA and a vendor UC; when a target breaches, the engine walks the chain and attributes the breach to the responsible team or vendor.
  • Coverage windows — named calendars per tenant (timezone, split shifts, holidays, 24×7, or a follow‑the‑sun union of several regional windows).
  • Priority‑ordered matching rules with a reorder endpoint and a match‑preview so admins can see which rule a ticket will hit before saving.
  • Immutable event log — every start/pause/resume/warn/breach/met/stop is an append‑only sla_events row; multi‑condition pause (e.g. waiting‑on‑customer and waiting‑on‑vendor) is tracked separately from a hard stop.
  • Reporting — compliance %, attributed breach report, an at‑risk live board, and cycle‑time percentiles, all backed by a nightly sla_metrics_daily rollup, plus an AI breach‑risk score per active instance.

02

On‑Call & Incident Response

built

Shipped 2026‑07‑02. A PagerDuty‑style layer: who's on call, how alerts get routed and escalated, and a structured incident‑command workflow with an auto‑built timeline.

What it does

  • Services, schedules, layers & overrides — define an oncall_service, attach rotation layers and one‑off overrides, and resolve “who's on call right now” at any timestamp.
  • Alerts with dedup — inbound alerts (generic or provider webhooks) are deduplicated and routed via alert_routing_rules before paging fires.
  • Escalation policies — multi‑step escalation over contact_methods and notification_rules, delivered through pages on a dedicated paging pipeline, plus heartbeats for dead‑man's‑switch monitoring.
  • Incidents — one‑action declare from an alert, a ticket, or cold‑start; a year‑scoped IR‑2026‑NNNN sequence distinct from ticket numbers; roles (Incident Commander, Comms, Ops, Scribe) auto‑staffed from on‑call; an immutable timeline and status‑update feed.
  • Blast radius — a CMDB recursive‑CTE walk shows what else is impacted by the affected asset/service.
  • Public status page — an unauthenticated read path with per‑tenant config and maintenance‑window suppression exists in the API, but has no screen anywhere yet in the web app, itsm‑app, or mobile — see “Not built yet.”
  • Workflow engine — declarative trigger → condition → action automations (SLA warn/breach, alert created, incident declared, severity changed) with dry‑run and a run history.
  • SRE extras — AI‑assisted post‑incident‑review drafts, responder suggestions, and MTTA/MTTM/MTTR + on‑call‑load + alert‑noise reports.

03

SLI / SLO & Error‑Budget Reliability

built

Shipped 2026‑07‑02, docs 2026‑07‑06. A deliberately separate layer from ticket SLAs — a ticket SLA measures support timeliness; an SLO measures service reliability. Telemetry‑fed, attached to Module 02's services, and reusing its alert/paging rails rather than the ticket‑SLA engine.

The model

SLI (what's measured, e.g. good ÷ valid requests) → SLO (the internal target, e.g. 99.9% over a rolling 28 days) → error budget (100% − SLO, the failure allowance) → burn rate (how fast that budget is being spent — 1.0 tracks the window exactly, 14.4 spends 28 days of budget in 2). The customer‑facing SLA sits on top, deliberately looser than the internal SLO so the team reacts before the contract is at risk.

What it does

  • SLI sources — Prometheus, Datadog, an HTTP uptime probe, a log query, an internal metric, or a signed push API; each defines a good/valid query or event match.
  • SLO objectives — availability, latency, error‑rate, freshness, or custom, targeted at a percentage over a rolling or calendar window, attached to a service from Module 02.
  • Immutable measurement buckets — time‑bucketed good/total counts; budget consumed, current SLI, and burn rate are all derived from these on read, never stored, so they stay reproducible.
  • Multi‑window, multi‑burn‑rate alerts (the Google SRE pattern) — a fast burn (e.g. 2% of budget in 1h) pages on‑call through Module 02; a slow burn (e.g. 10% in 6h) opens a ticket instead of paging.
  • Ingestion both ways — a Celery‑beat pull adapter per source type, or a signed push endpoint for external systems to report counts directly.

04

Support Recording + RCA Governance

builtphase 1–2 of a 5‑phase spec

UI shipped 2026‑07‑19; cross‑tenant fixes and full mobile parity 2026‑07‑27; demo data seeded 2026‑07‑29. Two halves that share one goal: every important support interaction is attached to the ticket, and every serious failure has an auditable, approved RCA.

4A · Support Recording

  • Manual link‑from‑URL — an agent pastes a Teams, SharePoint, or OneDrive meeting‑recording link onto a ticket; the URL's host is validated and metadata (title, organizer, participants, timing) is captured.
  • Consent & sensitivity gating — tenant‑level recording policy governs whether consent is required, and a recording can be flagged contains_pii, contains_credentials, or legal_hold, which blocks AI summarization for that recording.
  • Access policy + access log — visibility is scoped (ticket team / assigned agent / manager / customer / restricted); every open, download, or summary‑generation is written to an insert‑only access log.
  • AI summary — asynchronous, budget‑gated, and generated from the recording's title/description text (not a fetched transcript — see “Not built yet”).
  • Mark as RCA evidence — a one‑toggle promotion that links the recording into an RCA's evidence checklist.

4B · RCA Governance

  • Policy‑driven, not manually remembered — an admin policy builder defines condition rows (ticket type, priority, SLA breach, repeat‑incident count, …) with a dry‑run test, so RCA gets auto‑required by rule rather than by someone happening to notice.
  • Governed state machine — required → draft → under_review → approved → actions_in_progress → completed, with rejected (back to draft), waived (manager/admin only, reason required), and a system‑computed overdue flag. Invalid transitions are rejected outright.
  • Evidence checklist — required evidence types (timeline complete, recording linked if one exists, SLA breach evidence, customer impact documented, …) must be satisfied or explicitly waived before an RCA can move forward.
  • Action items (CAPA) — corrective/preventive actions with an owner, due date, and priority; high/critical items need verification before closure, or an explicit accepted‑risk sign‑off — an RCA cannot silently reach “completed” with open required actions.
  • AI draft, human‑approved — an AI‑drafted executive summary, timeline, and candidate root‑cause categories that the owner must accept or reject; never auto‑finalized.
  • Insert‑only history — every field change on an RCA is an append‑only audit row.
A modelling note worth knowing There is no separate rca_records table. The existing incident‑retrospective record doubles as the governed RCA via an is_rca_governed flag, and RCA action items reuse the retrospective's action‑item table rather than a new one. Functionally this is the full RCA workflow the spec describes — just built by extending an existing entity instead of introducing a parallel one.

Not built yet

Specced, and in some cases scaffolded in the data model, but with no working implementation today. Useful to know before promising any of these to a customer.

Deferred capabilities
  • Public status page UI — the API (admin config + unauthenticated public read) is complete, but no screen exists in the web app, itsm‑app, or mobile.
  • Microsoft Graph automated recording ingestion — today a recording only enters the system if an agent pastes its URL. Auto‑discovery/suggestion of Teams recordings by meeting subject, participants, or ticket‑number‑in‑title (spec §3.4.3, Phase 3) isn't built.
  • Real transcript fetch & dedicated redaction pipeline — AI summaries are generated from the recording's title/description only; the transcript‑fetch + PII/credential/SSN redaction step described in the spec doesn't run because there's no transcript to redact yet.
  • Legal hold enforcement — legal_hold exists only as a sensitivity flag that blocks AI summarization; there's no retention lock that prevents deletion.
  • RCA similarity search & automated quality check — “similar past RCAs” and an AI pass flagging vague root‑cause statements or missing owners are specced but have no route or service function yet.
  • Distinct RCA templates entity — sections/required‑fields are implied by policy today rather than a separate, admin‑editable template object.

Glossary

SLA / OLA / UC
Service‑Level Agreement (customer‑facing), Operational‑Level Agreement (internal team), Underpinning Contract (vendor) — three kinds of the same “agreement” object, chainable so an SLA breach can be attributed to whichever OLA/UC actually missed its target.
Coverage window
A named calendar (timezone, work hours, holidays) that SLA clocks pause outside of; several windows can be unioned for follow‑the‑sun coverage.
SLI
Service Level Indicator — the raw measured ratio, e.g. good requests ÷ valid requests.
SLO
Service Level Objective — the internal target for that SLI over a rolling window, e.g. 99.9% over 28 days.
Error budget
The allowed failure rate — 100% − SLO — spent down by real failures; when it's exhausted, a change‑freeze is warranted.
Burn rate
How fast the error budget is being consumed relative to a steady pace; a fast‑burn alert pages on‑call, a slow‑burn alert just opens a ticket.
Blast radius
The set of services/assets impacted by an incident, walked recursively through the CMDB dependency graph.
RCA
Root Cause Analysis — here, a governed workflow (not a document): required evidence, an approval gate, and tracked corrective/preventive actions before it counts as complete.
CAPA
Corrective and Preventive Action — an RCA action item with an owner, due date, and (for high/critical items) a required verification step.
Evidence checklist
Per‑RCA list of required evidence (timeline, recording, SLA breach data, customer impact, …) that must be provided or explicitly waived before the RCA can proceed.
