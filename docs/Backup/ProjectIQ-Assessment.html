Executive Summary
The Short Version
Architecturally the platform is in good shape: stateless app tiers, an async multi-tenant service with row-level security, real-time messaging on a Redis bus, and a clean SSO model. The gaps are operational — production deployment topology, secrets hardening, and observability — not design.
B+
Scalability
App tiers are stateless and horizontally scalable. Blocked only by single-worker default and single DB primary — both config/deploy changes, not rewrites.
A−
Performance
Async FastAPI + Redis caching + indexed queries. Major latency bug (IPv6 resolution) fixed. Frontend ships one 517 KB chunk — the main remaining win.
A−
Security (Design)
OIDC SSO, JWT validation, DB-enforced RLS as a non-superuser role, GDPR masking, rate limiting. Strong foundation.
C+
Security (Ops)
Default dev credentials, no TLS/headers in-app, secrets only partially in Infisical, no formal audit/pen-test. Must close before public exposure.

Scalability
How Fast Can We Scale Up?
Per-component effort to add capacity. The platform is designed to scale horizontally; most levers are configuration and deployment topology, not code.
ITSM ServiceFastAPI · stateless
Add replicas behind a load balancer. JWT-authed, no server session — any instance serves any request. DB pool sized per replica.
Easy · hours
Chat / Portal (Flask+SIO)eventlet workers
Raise GUNICORN_WORKERS and enable the Redis bus so Socket.IO rooms sync across workers. Background threads pinned to worker 0 (already handled).
Easy · config
Celery Workersasync jobs
Scale worker containers horizontally; Redis broker fans out. Beat stays singleton.
Instant
Rasa Core + ActionsNLU runtime
Run multiple Core replicas (external Postgres tracker store already configured) + N action servers behind LB.
Medium
FrontendsReact / Expo
Static bundles → push to CDN / object storage. Effectively unlimited horizontal scale.
Instant
PostgreSQL (both)stateful
Introduce pgBouncer pooling + read replicas; route reads to replicas. Writes remain single-primary until partitioning/sharding is justified.
Hard · plan
Rediscache / bus
Vertical first; Redis Cluster / Sentinel for HA when the bus becomes critical-path.
Medium
MinIOobject store
Distributed MinIO (erasure coding) or swap for managed S3 — presign client already abstracted from the internal client.
Medium
Bottom line: from a cold "single box" to a horizontally scaled deployment is mostly a topology + config exercise (LB, Redis bus on, more replicas, pooler, replica DB). The two true ceilings are single-primary write throughput and Keycloak/Redis HA — both addressable with standard infra patterns, no application rewrite.

Security
What's Done · What's Needed
The application-layer security model is strong. The remaining items are operational hardening that must close before any public/production exposure.

✅ In Place

  • Keycloak OIDC SSO — chatbot is SSO-only, no passwords stored
  • JWT Bearer validation on every ITSM request; JWKS verified
  • Role-based access: IAM roles synced to the ITSM DB on login
  • Multi-tenant Row-Level Security enforced by PostgreSQL
  • Runtime connects as non-superuser itsm_app so RLS can't be bypassed
  • GDPR masking of passwords / card numbers / IBANs in handoff context
  • Presigned object URLs — bucket is never public
  • Rate limiting + request logging middleware on ITSM
  • CORS allowlist; silent-check-sso route for iframe SSO
  • Org policy: secrets/keys forbidden in prompts (placeholders only)

⚠️ Needed

  • Replace default dev credentials (minioadmin, DB passwords) HIGH
  • TLS termination + HSTS / CSP / security headers at the edge HIGH
  • Complete secrets migration into Infisical (currently partial) HIGH
  • Audit-log retention + tamper-evident storage MED
  • Dependency / image vulnerability scanning in CI MED
  • Per-tenant / per-role rate-limit tuning & abuse controls MED
  • Formal pen-test & threat model sign-off MED
  • MFA enforcement via Keycloak policies LOW
  • Backup / disaster-recovery runbook for both DBs + MinIO LOW
  • WAF in front of the edge LOW
