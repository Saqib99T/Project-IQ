Pre-flight checklist (do this before the audience joins)

  • itsm-service stack up: docker compose up -d db redis minio api from D:\99T\Code\itsm-service — confirm curl :8000/api/v1/health returns 200.
  • Demo data present: re-run the three seed scripts if this is a fresh DB (scripts/seed/DEMO_DATA_SUMMARY.md) — Act 3's RCA walkthrough depends on the 5-stage pipeline seeded on the Blue Team tenant.
  • web_api / portal / itsm-app / widget running on port 8181 (start_local.ps1 or your usual local launch).
  • Four separate browser sessions ready — use 4 browser profiles or 4 incognito windows, one per persona. IAM SSO cookies will otherwise clobber each other mid-demo.
  • Open the seeded incident directly if possible — Blue Team's "Payments API outage" (RCA‑2026‑0001) — so Act 3 doesn't burn time navigating.
Rehearse it unattended first scripts/demo-automation/ is a Playwright suite that plays through all four acts against the real app with these exact logins — npm run all from that folder. It doubles as a pre-flight check (if it fails, the live demo will too) and records a .webm video per act under recordings/ as a fallback if you'd rather not risk live-clicking. See that folder's README for setup.

ACT 1 of 4

Tenant User — "I have a problem"

~6 min blue.bot@example.com Chat widget
  1. Open /bot, sign in with blue.bot@example.com. If a product picker appears, pick one — sessions are scoped per product.
    This is the same chat surface an employee sees embedded in their intranet — signed in via single sign-on, not a separate password.
  2. Ask a real question the KB covers (e.g. "how do I connect to the VPN?") — let the bot answer from the knowledge base with quick-reply buttons, not a ticket.
    Most requests never need a human — bot-first, ticket only when it's actually needed.
  3. Trigger ticket creation — either ask something outside the KB or use the ticket quick-issue chips. Fill the form (title, a quick-issue chip, priority) and submit. Note the ticket number — Act 2/3 reopen this exact ticket.
  4. Ask for a human — trigger handoff (e.g. "talk to a person" or let a low-confidence reply escalate). Show the queued state: position, estimated wait.
    This is the exact moment we'll pick up from the other side of the screen in Act 2.
If handoff won't trigger: most bot flows have an explicit "talk to a human" quick-reply — use that instead of relying on low-confidence detection.
ACT 2 of 4

Tenant Operator — "I handle it"

~8 min blue.opt@example.com Operator Console ITSM (agent)
  1. New browser session → /portal, sign in with blue.opt@example.com. This routes straight to the Operator Console.
  2. Queue — show the waiting session from Act 1: trigger reason, priority badge, wait time, product badge. Click Accept to claim it.
  3. Session view — reply to the user's message; open the Canned panel and send one; then try the AI-draft co-pilot — generate a suggested reply, edit it, send.
    Nothing here is fully automated — the operator always reviews and sends. AI drafts, it doesn't decide.
  4. Click Resolve. Switch back to the Act‑1 window to show the star-rating prompt that appears for the user.
  5. Back in the Operator Console, open the ITSM Tickets tab and pull up the ticket created in Act 1 by number. Add an internal note (the internal/public toggle only appears at agent tier and above — end_user never sees it) and change its status.
    Same login, same person — this is the ITSM "agent" tier, not a separate system.
  6. Point out the ticket's live SLA panel — countdown, % consumed — visible to everyone, but only agent+ can act on it.
If the AI-draft button is empty/slow: it's budget-gated and async — have a canned response ready as the fallback beat.
ACT 3 of 4

Tenant Admin — "I run the operation"

~12 min — the centerpiece blue@example.com Portal ITSM (admin)
  1. New browser session → /portal, sign in with blue@example.com. Tour quickly: Analytics, History (cross-session interaction log), Live Monitor, Users (invite/manage own org).
  2. Integrations — open the self-serve marketplace. Show a connected service card (SSO/storage/email — read-only status) and then configure a webhook connector (Teams or generic) — URL, secret, event checkboxes.
    This used to be platform-only. Tenant admins can wire their own integrations now, scoped to just their org.
  3. Switch to /itsm, same login. Open Administration and walk the groups: Service Catalog (SLA/OLA/UC), On-Call & SRE (On-Call/Escalation, Reliability (SLO), RCA Governance), People & Access, Automation. Point out the lock icons — some sections stay admin-only even for a manager tier.
  4. Reliability (SLO) — show the error-budget gauge on the seeded Payments/Web services (one meeting target, one at-risk) and a burn-rate rule.
  5. Incidents — open the Payments API outage incident, scroll to the RCA panel. This is RCA‑2026‑0001: full evidence checklist provided, both action items verified, AI draft accepted.
    This is the whole point of RCA governance — not a text box, a workflow. Evidence, approval, tracked actions, all before it's allowed to say "completed."
  6. Jump to the Admin → RCA Governance screen. Open the pipeline/dashboard view and show the other four seeded RCAs in different states — actions_in_progress with an overdue action item, under_review blocked on a consent-disputed recording, overdue with an inaccessible recording, and one the manager waived with a reason on record.
    Five real records, five different places in the lifecycle — this isn't a demo of one happy path, it's what an actual queue looks like.
  7. Open ticket #90008 ("Payroll app slow"), go to the Recordings tab — show the linked recording flagged sensitive, its AI summary skipped for consent reasons. Then open ticket #90001 and show a normal, fully-summarized recording for contrast.
  8. Reports — scroll to the RCA/recording compliance stats added there.
If this act runs long: it's fine — this is the centerpiece. Trim Act 4 instead, not this one.
ACT 4 of 4

Super Admin — "I run the platform"

~6 min projectiq-admin@99technologies.com Portal — Platform group
  1. New browser session → /portal, sign in with projectiq-admin@99technologies.com. Point out the extra sidebar group that only this login sees: Platform — Organizations, Configuration, Knowledge Base, Bot Studio, Themes, Observability, Diagnostics, Inspector, Routing Rules.
  2. Organizations — the cross-tenant list (read-only, no "create org" button — tenants provision via a signed IAM webhook, not this UI). Point out Blue Team and Green Team side by side with independent waiting/assigned/resolved stats.
  3. Use the tenant switcher in the header — flip from Blue Team to Green Team. Everything reloads scoped to Green — different tickets, different users, same product.
    This is the whole multi-tenant guarantee in one click — row-level security, not just a UI filter.
  4. Routing Rules — show a handoff routing rule (match intent/keyword/app → target queue + priority boost) — platform-level, shapes every tenant's queue behavior.
  5. Brief mention only (don't deep-dive): Bot Studio, Observability, Config — these are platform engineering surfaces, not usually demo material for a business audience.

Bonus beat — mobile (30 seconds, optional)

The Expo mobile app mirrors the chat widget (same IAM SSO, same handoff flow) and adds one manager-only touch worth a single screenshot or 30-second live moment: from a ticket's "View Ticket" action, a manager-tier login can review and Approve / Reject / Waive an RCA right from their phone. It has no admin/platform surface at all — position it as "support access from your pocket," not a fifth persona.

Closing & recap (2–3 min)

One ticket, one thread: an employee asked a question in Act 1, an operator resolved it live in Act 2, an admin turned a real incident into a governed RCA with tracked evidence and actions in Act 3, and a platform admin showed the isolation and control that makes all of it safe to run across many tenants at once in Act 4. Same login system end to end — no separate "admin app."
