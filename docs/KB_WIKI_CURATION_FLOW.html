KB Wiki Curation + Federated RAG — How It Works

Spans two repos: itsm-service (curation/authoring) and Project-IQ-V2 (bot query path). This reflects the real, current implementation — several phases diverged from the original plan once real code was checked; see docs/plans/KB_WIKI_CURATION_RAG_PLAN.md for that history.
The 30-second version: content gets curated in itsm-service by an AI pipeline that always pauses for human review before publishing. The bot in Project-IQ-V2 searches that curated index first, falls back to a local index for content that never reaches itsm-service, and — this is the loop-closing part — logs every question it couldn't answer so a recurring gap can turn into a new draft article automatically.

01 Content curation (itsm-service) — how an article gets written

Three independent triggers feed one shared synthesis pipeline. A human always reviews before anything goes live.

Trigger A
Manual
An agent pastes raw text via POST /api/v1/kb/curation/run — has content but wants it turned into a proper article.
Trigger B
Ticket resolved
Nightly beat job auto_draft_kb_from_tickets. Replaces the old single-LLM-call KBDrafter outright — one synthesis mechanism now, not two.
Trigger C
KB gap feedback
Nightly beat job cluster_kb_gaps_and_draft — clusters of ≥5 similar unanswered bot questions in 7 days become a draft automatically.

02 Bot query path (Project-IQ-V2) — how a question gets answered

Auth scoping on the primary search: a logged-in user's own IAM JWT is forwarded, so itsm-service scopes results to that tenant's private + public content. An anonymous user (no token) is scoped to global public only (tenant_id IS NULL AND visibility = public) — no special auth mechanism, just a query-scoping rule.
Why two search paths instead of one: itsm-service's chunked index (kb_chunks, heading-aware chunks + text-embedding-3-small embeddings) is the system of record and does real RAG-grade search — it's primary. The local vector_search.py index is a deliberate fallback, kept alive because Firecrawl scraping and source extensions (Google Sheets / Website / MS Teams) write content straight into Project-IQ-V2's own DB and never reach itsm-service — without the fallback, that content would be permanently unsearchable.

03 The full loop, end to end

A question the bot couldn't answer today becomes, after enough repeats, a candidate KB article the bot can answer tomorrow — without anyone manually noticing the pattern.

flowchart LR
    Q["Bot query"] -->|answered| A["User gets help"]
    Q -->|"KB miss (logged as gap)"| G[("kb_search_gaps\ntable, Project-IQ-V2")]
    G -->|"nightly: cluster_kb_gaps_and_draft\nreads PIQ's DB directly"| C["itsm-service curation pipeline\n(same KBCurator graph as §1)"]
    C -->|human approves| P["New published article\n+ chunked + embedded"]
    P -->|next similar query| Q
