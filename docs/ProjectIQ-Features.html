🎫 ITSM End
A Full ITSM + SRE Service — Not Just Tickets
A dedicated FastAPI microservice owns the service-management domain — now spanning SLA/SLO governance, PagerDuty-style on-call & incident response, and policy-enforced RCA governance with Teams recording evidence: independently deployable, independently scalable, multi-tenant to the core.
🎫
Ticketing
Full lifecycle — create, read, list & filter, assign, comment, status transitions, resolve and close — with categories, priorities and product tagging.
⏱️
SLA / OLA / UC Engine (SLM)
Agreements of three kinds — customer SLA, internal OLA, vendor UC — each with per-metric targets (first-response, resolution, time-to-mitigate…). Priority-ordered rules auto-attach the right agreement; a per-ticket clock counts only inside its coverage window (24×7 or business hours), warns at 50/75/90%, then meets or breaches. Breaches are attributed down the OLA/UC chain, and an AI predictor flags likely breaches before they happen.
🚨
On-Call & Escalation
PagerDuty-style on-call: services, severity levels, and rotating schedules (daily / weekly / follow-the-sun) whose current responder is resolved on the fly. Escalation policies step a page from the on-call schedule → a user → a team with timeouts, and alerts dedup, route and auto-escalate until acknowledged. Contact methods per responder; heartbeats catch silent failures.
🧯
Incident Response
Declare an incident from an alert or by hand, staff it with the four roles (IC / comms / ops / scribe), and drive a validated lifecycle (declared → investigating → identified → monitoring → resolved → postmortem → closed). Every change lands on an immutable timeline; audience-scoped status updates (internal / stakeholder / public); blast-radius from the CMDB; and a templated PIR / retrospective with action items that push to follow-up tickets.
📈
SLO & Error Budgets NEW
The SRE reliability layer: define an SLO (e.g. 99.9% availability over 28 days) on a service, fed by an SLI source (internal metric, push API, uptime probe, Prometheus/Datadog). The engine derives the error budget, current SLI and burn rate live, and fires multi-window burn alerts — fast-burn pages on-call, slow-burn opens a ticket — through the same on-call rails.
🔍
RCA Governance NEW
RCA isn't a text box, it's a workflow: a policy builder auto-requires one by rule (major incident, critical SLA breach, repeat failures), then drives a governed lifecycle (required → draft → under review → approved → actions in progress → completed, plus rejected/waived/overdue). Approval is gated on an evidence checklist (timeline, customer impact, linked recording, SLA breach data…) and every corrective/preventive action needs owner-verified completion — or an explicit accepted-risk sign-off — before an RCA can quietly call itself done. An AI draft assists but never decides; every field change is an append-only audit row.
📼
Support Recording Evidence NEW
Paste a Microsoft Teams, SharePoint or OneDrive recording link onto a ticket in one step — metadata and a secure link are stored by default, not the video itself. Each recording carries consent and sensitivity flags (PII, credentials, legal hold) that gate an async AI summary and restrict access; every view, download or summary generation writes an insert-only access log. One toggle promotes a recording straight into an RCA's evidence checklist.
👥
Teams & Smart Assignment
Organize agents into teams and route work; an auto-assign action hands new tickets to the least-loaded team member. Per-team open volume and average age tracked.
✨
AI Ticket Enrichment
Automatic classification (accept/reject) and duplicate detection with dismiss — plus an exportable classification dataset for continuous improvement.
🗨️
Virtual Agent
A built-in AI assistant with multi-turn sessions and real-time streaming (SSE) responses, scoped to the authenticated tenant.
⚙️
Automation Engine
No-code rules: trigger → condition → action (assign team/user, auto-assign least-loaded, set priority, escalate, notify), with execution logs and a dry-run test.
✅
Approval Workflow
Change & access-request tickets enter pending_approval, open an approval and fire the trigger; a manager/approver decides via a dedicated endpoint that drives the validated transition — direct status edits are blocked.
🧩

Always-On
Real-time & Self-Healing
A Socket.IO backbone keeps every client in sync, and background workers keep the queue fair, fresh and consistent — automatically.

⚡ Real-time backbone

  • Socket.IO over eventlet with a Redis message bus for multi-worker fan-out
  • Non-blocking DB driver — queries cooperatively yield, so the event hub never stalls
  • Room routing — per-user, per-operator, per-conversation & queue-overview rooms
  • Live events — queue updates, assignment, messages, typing, wait refresh, resolution
  • Sub-second delivery — handoff & messages relay in milliseconds, even under load

🩺 Background workers

  • Queue timeout / SLA — alerts, "remain or leave email" prompts & auto-abandon
  • Wait refresh — recalculates every waiting user's position & ETA
  • Priority boost — nudges long-waiting items up to prevent starvation
  • Heartbeat watchdog — marks unresponsive operators offline
  • Orphan-state healer — repairs any conversation stuck between states

🔎 Tracing & alerting

  • End-to-end correlation IDs — one request id threads admin API → NLU → action server → ITSM
  • Structured logging — every line stamped [req=…], so one grep reconstructs a whole turn
  • Error alerting — ERROR-level events notify operators & admins, deduplicated & storm-capped
  • Honest error rate — measured from real action failures, not guessed from bot wording

Trust & Compliance
Security & Privacy
Security is enforced server-side at every layer — never left to the client.

🔐 Authentication

SSO-only via Keycloak; stateless JWTs validated against the realm; separate operator-token flow. No passwords stored by the app.

🚧 Authorization

Per-tenant scoping enforced on every endpoint; role & platform-org gating; super-admin tenant override only for platform members.

🕵️ GDPR & privacy

Consent gate before handoff; transcripts masked for passwords, card numbers & IBANs; data-subject endpoints in ITSM.

🧱 Data integrity

Parameterized queries throughout; tenant identity sourced from the JWT, never the request body; row-level isolation in ITSM.

📝 Auditability

Handoff state-log records every transition; consent log; automation execution logs; AI token-usage accounting.

🗄️ Secure storage

Attachments via signed, expiring URLs proxied through the app port — object storage is never exposed directly to the browser.

🚦 Rate limiting

Per-IP limits tiered by route (auth / chat / default), backed by Redis in production with an in-memory fallback — a dependency-free limiter, tunable by config.

🔑 Secrets & supply chain

No secrets in the repo — injected via env at runtime (PIQ_* overrides); Dependabot + weekly pip-audit in CI; signed Microsoft Teams payloads use the incoming-webhook URL as the secret.

⚙️ Action Server
Custom actions — tickets, KB, handoff, ITSM calls

Type:ConfigOps≈ minutes

Type:Ops / Deploy≈ minutes–hours
🐘 Database
PostgreSQL + pgvector — single source of truth
 Add read replicas and route heavy reads (analytics, queue, history); pooling multiplexes many clients onto a few connections; optional HA (Patroni/repmgr) for auto-failover.
Type:Infra≈ hours (HA: ½–1 day)
 Bigger CPU/RAM/IOPS/SSD, larger pgvector indexes & pool sizes, and major-version/extension upgrades — the app talks to the pooler, so the DB upgrades behind it.
Type:Planned windowscheduled
🎫 ITSM Service
Independent FastAPI microservice
 Scale its own replica set independently of the bot for ticket-heavy tenants; horizontally stateless behind the same-origin proxy.
Type:ConfigOps≈ minutes
 Add resources per replica and deploy new versions on its own release cadence — it shares only the identity layer, not the chatbot's lifecycle.
Type:Ops / Deploy≈ minutes–hours
🔴 Redis & Real-time
Socket.IO message bus + cache
 Add app workers — the Redis bus fans Socket.IO events across all of them; Redis Sentinel/Cluster removes the single point of failure.
Type:OpsInfra (HA)≈ minutes–hours
 Increase the Redis memory/persistence tier and raise worker counts as traffic grows; in-process TTL cache provides a graceful fallback.
Type:Infra≈ minutes–hours
Because every tier is stateless and decoupled, you scale only the bottleneck. The usual first lever is the NLU service (CPU-bound, lowest effort to scale out); the database is rarely the limit thanks to pooling, caching and replicas, and is the only tier that may need a planned maintenance window.
