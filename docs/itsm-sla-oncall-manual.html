The big picture

Six things work together. A person raises a ticket; an SLA clock governs how fast it must be answered and resolved. Monitoring raises alerts; the on-call rotation decides who gets paged; a serious alert becomes an incident that a team drives to resolution and then reviews. The knowledge base and asset register support all of it.

The one rule that explains "why can't I see anything / why the error"

Every record belongs to a tenant (an organisation). What you see depends on how you sign in:

  • Tenant user (you belong to one org) → you see only your org's data. Admin screens that configure one org at a time will ask you to pick a tenant first.
  • Platform / 99T staff with no tenant selected → you see all tenants at once ("show all"). Pick a specific tenant from the switcher to narrow down.

If a list is empty, you're almost always on the wrong side of this rule — switch tenant (or clear it) and it appears. The old Tenant context required / "unexpected error" on these screens has been fixed.

Module 01

SLA & Service-Level Management

An SLA is a promise with a clock: "we'll respond within 15 min and resolve within 4 h." The engine attaches that clock to each ticket automatically, counts down only during agreed working hours, warns you as it runs low, and marks a breach if time runs out.

How it works

Agreement▸ Targets (metric + time)▸ Rule matches a ticket▸ Clock (SLA instance) runs▸ Warn → Breach / Met
  • Agreement — the contract. Three kinds: SLA (you → customer), OLA (team → team, internal), UC (vendor → you). OLAs/UCs underpin an SLA so a breach can be attributed to the responsible party.
  • Targets — the actual clocks on an agreement. Each has a metric and a duration: first_response, resolution, time_to_acknowledge, time_to_mitigate, and periodic updates. A target can apply only to certain priorities/types and uses a coverage window (24×7 or business hours).
  • Rules — decide which agreement a new ticket gets, top-down by position (e.g. "critical → Premium SLA, everything else → Standard").
  • SLA instance — the live clock on one ticket. It pauses automatically (e.g. waiting on the customer), warns at 50/75/90 %, then meets or breaches.

The states you'll see on a ticket

running warned paused met breached

How to use it — set up an SLA

📍 Administration → Service Catalog → SLA / OLA / UC  ·  tabs: Agreements · Rules · Coverage windows · At-risk

  1. On Coverage windows, create the calendars the clocks follow — e.g. a 24×7 window and a Business Hours (Mon–Fri 9–6) window.
  2. On Agreements, create an agreement (pick a kind — sla for customer-facing). Expand it to add targets: choose the metric, duration in minutes, coverage window, and (optionally) which priority it applies to.
  3. On Rules, add match rules in priority order so new tickets get the right agreement automatically. Top rule wins.
  4. Watch the At-risk board for the live count of at risk / breached tickets and the compliance %.

Day to day — on any ticket

Open a ticket (/itsm/tickets/…). The SLA panel shows each live clock counting down, its state pill, and an Override control for managers when a special case needs a manual due-date. Nothing to configure per ticket — matching is automatic.

Module 02

On-Call & SRE

This decides who gets woken up when something breaks. You define the services you run, a rotation of people who cover them, and an escalation policy that says "page the on-call person; if they don't answer in 15 min, page their manager."

How it works

Service▸ Escalation policy▸ Step 1: on-call schedule▸ Step 2: manager
  • Service — a thing you operate (e.g. Payments API). Alerts and incidents attach to a service; each service points at one escalation policy.
  • Schedule — a rotation. It has layers, each a list of participants who take turns (daily / weekly / follow-the-sun). The system computes who's on call right now on the fly — no manual calendar upkeep.
  • Escalation policy — an ordered list of steps. Each step targets a schedule, a specific user, or a team, with a timeout before it escalates to the next step. Policies can repeat.
  • Severity levels (SEV1 SEV2 SEV3) — set how loud the response is; high severities can auto-page and require certain incident roles.
  • Contact methods — how each person is reached (email, SMS, voice, Slack…).

How to use it — stand up on-call

📍 Administration → On-Call & SRE → On-Call / Escalation  ·  tabs: Services · Schedules · Escalation

  1. On Schedules, create a rotation (e.g. Primary On-Call Rotation, weekly), then add a layer and list the participants who take turns.
  2. On Escalation, create a policy and add steps: step 1 → your schedule (timeout 15 min), step 2 → a manager (notify all). Set a repeat count if you want it to loop.
  3. On Services, create each service you run and attach the escalation policy.
  4. Add severity levels and each responder's contact methods so paging can actually reach them.

Use the who's-on-call / preview control to confirm the rotation resolves to the right person before you rely on it.

Module 03

Alerts

Alerts are the raw signals from monitoring. The inbox is where you triage them: quiet the noise, acknowledge what you're handling, and promote anything serious into an incident.

How it works

  • An alert arrives with a dedup key — repeats of the same problem increment an occurrence count instead of spamming you with new rows.
  • Routing + the service's escalation policy decide who gets paged, stepping up if no one acknowledges in time.
  • An alert moves through open → acknowledged → resolved. Maintenance windows suppress paging for planned work.

How to use it — triage the inbox

📍 Incidents 🚨 → Alerts tab

  1. Scan open alerts (most recent first). Each shows its title, service and severity.
  2. Click Resolve once the underlying issue is cleared.
  3. If it's a real, customer-affecting problem, click Declare incident — this opens an incident already linked back to the alert.

Module 04

Incidents

An incident is the coordinated response to something broken. It gives the response a commander, a running timeline, stakeholder updates, and — afterwards — a review so the same thing doesn't happen twice.

How it works — the lifecycle

declared▸ investigating▸ identified▸ monitoring▸ resolved▸ postmortem▸ closed
  • Roles — who's doing what: IC (incident commander), comms, ops, scribe. One person per role.
  • Timeline — an immutable log of everything that happened; key moments can be pinned.
  • Status updates — messages aimed at an audience: internal, stakeholder or public (status page).
  • PIR / retrospective — after resolution, capture the summary, contributing factors and impact, then track action items (which can be pushed straight into a follow-up ticket).
  • Blast radius — which services and assets the incident touched, from the CMDB.
declared investigating monitoring resolved closed

How to use it — run an incident

📍 Incidents 🚨 → Incidents tab (master list on the left, detail on the right)

  1. Declare — from a serious alert (Alerts tab → Declare incident) or manually. Set a title and severity.
  2. Assign roles — name the IC first; add comms/ops/scribe as needed.
  3. Drive status — move it declared → investigating → … → resolved as the situation changes. Each change lands on the timeline.
  4. Post status updates — keep stakeholders informed; choose the audience.
  5. After resolution — click Generate PIR draft for a templated writeup, finish the retrospective, and log action items.

Module 05

Reliability — SLOs & Error Budgets

The SRE reliability layer, and the newest module. Where an SLA promises a customer a response time, an SLO is your internal reliability target for a service — e.g. "Payments API is available 99.9% of the time." The gap you're allowed to fail is the error budget; spend it too fast and it pages the on-call.

How it works

SLI source (the measurement)▸ SLO objective (target %)▸ Error budget + burn rate▸ Burn alert → Module B
  • SLI (Service-Level Indicator) — the raw measurement, good ÷ valid events. An internal_metric source computes it from data you already own (uptime, incident-free time, ticket-SLA compliance) — no external monitor needed. Other sources: push_api, http_uptime_check, Prometheus/Datadog.
  • SLO — the target on a service, e.g. 99.9% over a rolling 28-day window.
  • Error budget = 100% − SLO. At 99.9% you may fail 0.1% of events. The dashboard shows % remaining.
  • Burn rate = how fast you're spending it. 1× = exactly on pace to use the whole budget by window end; 14.4× = the whole 28-day budget gone in ~2 days.
  • Multi-window burn alerts — fast_burn (budget vanishing → pages on-call via Module B) and slow_burn (steady erosion → opens a ticket-grade alert). Both auto-clear when burn drops.
meeting at risk burn 1× burn 6× (slow) burn 14.4× (fast)

How to use it — define an SLO

📍 Administration → On-Call & SRE → Reliability (SLO)  ·  tabs: Error Budget · SLOs · SLI Sources

  1. On SLI Sources, add a source. The easy start is internal_metric → uptime (works immediately, no monitor to wire up).
  2. On SLOs, create an objective: pick the service, the SLI source, a target % and a window. Add a fast-burn and/or slow-burn rule so it can page.
  3. Watch the Error Budget board: each service shows its budget-remaining gauge, current SLI vs target, live burn rate and a meeting / at risk pill.
  4. Use simulate healthy / simulate outage on an SLO to see the gauge move and a fast-burn rule fire an alert into the Incidents inbox.

How it relates to SLA: the SLA sits on top and is deliberately looser (e.g. customer 99.5% + credits) so your internal SLO (99.9%) trips first — you react before the contract breaks.

Module 06

Knowledge Base & Assets

Knowledge Base

📍 Sidebar /itsm/kb · author under Administration → Knowledge Base

Articles live in spaces and categories, each with a visibility: public, internal or agents_only. The chatbot answers from the same KB, so a good article deflects tickets before they're raised.

Assets & CMDB

Assets have a category → type, a status, a vendor and an owner. Relationships (runs_on, connected_to, depends_on…) build the dependency map that powers an incident's blast radius.

Reference

Glossary

SLA
Service-Level Agreement — a timed promise to a customer (respond/resolve within X).
OLA
Operational-Level Agreement — an internal team-to-team promise that underpins an SLA.
UC
Underpinning Contract — a vendor's commitment to you that underpins an SLA.
Coverage window
The calendar an SLA clock runs against (24×7 or business hours); the clock ignores off-hours.
SLI
Service-Level Indicator — the raw reliability measurement of a service, good ÷ valid events.
SLO
Service-Level Objective — your internal reliability target for a service (e.g. 99.9% availability).
Error budget
The allowed shortfall (100% − SLO). Spend it and reliability work takes priority.
Burn rate
How fast the error budget is being consumed; 1× = on pace, 14.4× = 28-day budget gone in ~2 days.
Breach
An SLA clock that ran out before its target was met.
On-call
The person currently responsible for responding to a service's alerts.
Escalation
Automatically moving a page up the chain when no one responds in time.
Alert
A single signal from monitoring; deduplicated and triaged in the inbox.
Incident
A coordinated response to a real, impactful problem.
IC
Incident Commander — the single person in charge of the response.
PIR
Post-Incident Review (postmortem) — the writeup + action items after resolution.
MTTR
Mean Time To Resolve — an average used in reports to track response health.
CMDB
Configuration Management Database — your assets and how they depend on each other.
Tenant
One organisation. Isolation boundary for all data (see the orientation callout).
