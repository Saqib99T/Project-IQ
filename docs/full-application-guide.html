Overview

The product has three web surfaces sharing one Keycloak-backed identity (realm 99-iam, client project-iq) — the chat widget (/bot), the ITSM app (/itsm), and the portal (/portal, which itself contains both the operator console and the tenant/platform admin screens) — plus an Expo mobile app that mirrors the widget. Nobody has a separate password per surface: what a login can do is entirely a function of the IAM roles baked into their token.

This guide is organized by the four roles that actually matter to a demo or a rollout, not by every intermediate ITSM tier (there's also team_lead, functionally between agent and manager, differentiated mostly server-side rather than in the UI — not covered as its own section).

One identity, four surfaces

Every login's Keycloak token carries a project-iq client role and a tenant organization claim; the backend on each surface reads the same token and projects it onto that surface's own role vocabulary. There's no separate "admin app" — it's one token, read four different ways.

01

Tenant User

end_user

The employee asking for help. Signed in via SSO, no admin surface, no ticket-management controls — just get an answer or get connected to a person.

Chat widget /bot

  • Bot-first Q&A — messages go to the KB/NLU engine first; replies come with quick-reply buttons, KB article cards, and charts, not just text.
  • Product-scoped sessions — a picker gates chat until a product is chosen; each session id encodes user + product + a login epoch, so a fresh sign-in always starts a clean history record.
  • Ticket creation from chat — quick-issue chips, title/detail/category/priority, one file attachment (max 1MB), confirm before submit.
  • Human handoff — request a person anytime; see queue position and a live wait estimate; live typing indicator once connected; star-rating after resolution.
  • Session history — browse and reopen past conversations; missed operator messages back-fill on reconnect.
  • Guardrails — profanity/PII/SSN/credit-card/length input filtering before anything is sent.

ITSM app /itsm

  • Same sidebar as everyone — Tickets, Assets, Knowledge Base, Reports, Incidents, Notifications — minus the Administration link. Reports and Incidents aren't nav-gated at all, so an end_user's sidebar looks nearly identical to an admin's.
  • Create and track own tickets — title/description/type/priority only; no assignee field.
  • Comments are always public — no internal-note toggle; that only appears at agent tier.
  • SLA clocks and RCA are read-only — visible, not actionable.

02

Tenant Operator

Operator → agent tier

The IAM Operator client role is server-mapped onto the ITSM agent tier — same login, same person, two role vocabularies. Not a separate identity from an ITSM "agent"; it's the same one, viewed from two surfaces.

Operator Console /portal (routes at /operator/*)

  • Queue — waiting conversations with trigger reason (user request, low confidence, frustration detected), priority, wait time, product; claim with one click.
  • Session view — two-sided live transcript, typing indicator, resolve/release/transfer to another operator, session notes.
  • Canned responses — reusable replies, managed per operator.
  • AI-draft co-pilot — a suggested reply the operator reviews, edits, and sends — never auto-sent.
  • Presence — Available/Away/Busy/Offline status with a heartbeat.
  • ITSM Tickets tab — work ITSM tickets without leaving the console.

ITSM app /itsm — agent tier

  • Internal/public comment toggle — the one capability that appears exactly at this tier and not below.
  • Ticket edits — status, assignee, team, priority (server-enforced at agent-or-above; note below).
  • Still no Administration link — that only appears from manager tier up.
A gap worth knowing about The ticket edit panel (status/assignee/team/priority) is not hidden client-side for lower roles — it renders for everyone, and an end_user's edit attempt is rejected server-side (403). Cosmetic only, but worth knowing before a demo so a stray click doesn't look like a bug.
Where to find it Portal › Operator Console (auto-routed on login)
ITSM app › /itsm — same login, agent tier
03

Tenant Admin

org_admin → admin tier

Everything a tenant owns and can self-serve — pinned hard to their own org server-side. No cross-tenant visibility, no tenant switcher; those only appear for the platform identity.

Portal admin /portal (routes at /admin/*)

  • Organization group — Overview, Analytics, History (cross-session interaction log), Live Monitor, Alerts, Users (invite/manage own-org users only — can't grant Admin role or target another org).
  • ITSM group — shortcuts into Tickets/Assets/Knowledge Base/Reports.
  • Integrations marketplace — self-serve since a 2026 change (previously platform-only): connected-service status cards (SSO, storage, email, AI) plus installable webhook connectors (Microsoft Teams, generic webhook) with HMAC-signed delivery, scoped automatically to their own org.

ITSM app /itsm — full admin

The Administration menu, in full — everything below the manager tier still has locked (admin-only) items shown greyed out with a tooltip; a true admin login unlocks all of it.

04

Super Admin

platform_admin (via platform-org membership)

Cross-tenant reach, granted to anyone who's org_admin of the platform's own organization — not a distinct realm role. One extra sidebar group appears; everything else the tenant admin already had access to, this identity also bypasses into.

Portal — Platform group /portal

  • Organizations — every tenant, side by side, with waiting/assigned/resolved/last-activity stats. Read-only — no "create org" button anywhere.
  • Tenant switcher — a header dropdown (invisible to a tenant admin) that reloads the whole portal scoped to a chosen org.
  • Routing Rules — handoff routing by intent/keyword/app/entity/regex → target queue + priority boost. Platform-wide, shapes every tenant's queue.
  • Configuration, Knowledge Base, Bot Studio, Themes, Firecrawl, Observability, Diagnostics, Inspector — platform engineering surfaces (handoff/session/SMTP/Redis/LLM/KB config, widget theming, crawler management, system health). Not usually demo material for a business audience, but exist and are platform-only.
Tenant provisioning is not a UI action There's no "create tenant" screen anywhere, including here. New tenants are provisioned by a signed IAM lifecycle webhook (a product.subscribed event) — idempotent, keyed on the IAM org id, and it also seeds default SLAs/sequences/a "General" KB space. Don't demo tenant creation through the UI; it doesn't exist by design.
Where to find it Portal › sidebar › Platform group (only visible to this identity)

Mobile (Expo app)

Four screens total — Chat, Notifications, Profile, Settings. The chat screen is a faithful mirror of the widget: same IAM SSO (Keycloak PKCE, biometric re-lock after backgrounding), same handoff flow, same guardrails. From a ticket's "View Ticket" action it resolves a ticket number to its record and offers Recordings/RCA modals — any signed-in user can view recordings and submit an RCA, but Approve / Reject / Waive stays gated to manager-tier logins, checked the same way the web app checks it. There is no admin or platform surface on mobile at all — it's end-user plus one manager-only touch, not a fifth persona.

Glossary

IAM
The shared Keycloak identity provider (realm 99-iam, client project-iq) every surface authenticates against — no local passwords anywhere in the product.
Client role
A project-iq-scoped Keycloak role (Bot, Operator, Admin) — the primary signal each surface reads to decide tier.
Realm role
A Keycloak role not scoped to one client — org_admin is the one that matters here, driving both ITSM admin tier and (for the platform org) platform access.
Organization claim
The tenant(s) a token is scoped to — what makes row-level tenant isolation possible without a separate login per tenant.
Products claim
Which product(s) — e.g. itsm — a token is authorized for; gates the product picker in chat and cross-surface access.
Handoff
The bot-to-human escalation path: bot_active → queued → assigned, driven by Socket.IO events.
Platform bypass
The portal's isPlatformAdmin check — true for the super_admin role or for an org_admin of the platform's own org — and grants access past every other role gate.
